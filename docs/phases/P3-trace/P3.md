# Phase 3 — Trace: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan slice by slice, task by task. Steps use checkbox (`- [ ]`) syntax for tracking. Each slice file `S-<nn>-*.md` in this folder is one unit of work with its own tasks; this file holds what every slice shares.

**Goal:** A team can ask, from the CLI or one local page, which slices, tests, commits, pull requests and files sit under a requirement, what touched a path, what is uncovered and what shipped, across every repository of a program: `slicekit graph` builds the traceability graph of `docs/spec/04-traceability-graph.md` deterministically from the kit's own IDs and git, and `trace`, `history`, `impact`, `uncovered`, `shipped` and `visualize` read it.

**Architecture:** One builder writes one file; everything else reads that file. `slicekit graph` (S-17) reads only the sources REQ-4.2 allows (the markdown under the docs root, `git log` on the default branch and on every `slice/*` branch, the state, verdict and journal files, the test files' lines that name a REQ ID, and pull request metadata through `getHost`, C-1) and writes the graph under the directory `kitPaths(root, cfg).graph` names, which init already ignores (D-23). Three files live there, none committed: the graph itself (graph.json), the build index (index.json) and the pull request cache (one cache/pr-<n>.json per pull request). <!-- slicekit:example -->

- **The graph file** is `{schemaVersion: 1, builtAt, defaultBranch, sha, repos, nodes, edges}`. `sha` is the default-branch commit the build walked to; `builtAt` is that commit's committer date (proposed decision 1 below), never the wall clock, so the same inputs give the same bytes. `repos` is `[{name, sha}]`, the program repository first as `.`, then each workspace repository (S-20).
- **A node** is `{id, kind, label, from, …attributes}`. `id` is `<kind>:<key>` (`requirement:REQ-4.1`, `slice:P3/S-17`, `commit:<40 hex>`, `file:src/a.js`, `pull-request:19`); `from` is where it came from, `<path>:<line>` for a file-derived node, the commit SHA for a commit, `#<n>` for a pull request. The kinds are REQ-4.1's fourteen plus `verdict` (proposed decision 2).
- **An edge** is `{kind, from, to, at}`; `at` is `<path>:<line>` or a 40-hex commit SHA (REQ-4.1). Each edge kind admits a fixed set of (from kind, to kind) pairs; `validateGraph` refuses anything else, and an edge whose endpoint is not a node is dropped with a warning before validation, so a dangling reference in a doc never fails the build.
- **Determinism.** Paths are repository-relative and POSIX; nodes are sorted by `id`, edges by `from`, `kind`, `to`, `at`, all by code-unit order (no `localeCompare`); keys are written in a fixed order, one node or edge per line. Two builds from the same inputs are byte-identical, and an incremental build is byte-identical to a full one.
- **Incremental build.** The index records the SHA each walked ref pointed at and a fragment per source: per commit `{sha, parents, date, subject, slices, files}`, per doc, state, verdict, journal or test file `{hash, nodes, edges}` keyed by its path and the SHA-256 of its bytes. A run walks `git log <current tips> ^<recorded tips>`, so only new commits; reads only files whose hash changed; drops fragments of commits no current tip reaches (a deleted slice branch) and of files that are gone; then assembles the graph from all fragments. `--full` ignores the index.
- **Pull requests.** Numbers come from the state files' `pr.number`, merge commit subjects (`Merge pull request #<n> from …`), squash subjects ending `(#<n>)` and `#<n>` in release records. Each is fetched once with `getPullRequest` and cached with the SHA the local files give for it (the state's `pr.headSha`, else the merge commit). A cached `MERGED` or `CLOSED` answer is final; an `OPEN` one is fetched again when that SHA moves. When the host cannot be reached the build continues from the cache and marks every pull request it could not refresh `stale: true`; without `gh` it prints `pull requests skipped: gh not found` (REQ-4.2).
- **Queries** (S-18, S-20) and **visualize** (S-19) never run git or call the host: they `loadGraph` and work on `indexGraph`, an in-memory index by id, by kind and by edge direction. A query is a `queryCommand({…})` from S-17's shared shell, which owns argument parsing, the missing-graph and unknown-ID refusals and `--json`.
- **Visualize** renders one self-contained HTML page: the graph inlined as an escaped `application/json` script block, one inline client script whose view functions return HTML strings (so a test runs them in `node:vm` without a browser), inline CSS, and a Content-Security-Policy meta that forbids loading anything external. `slicekit visualize --write <file>` writes it; without `--write` it serves the same page and the graph from `node:http` on 127.0.0.1.

S-17 (group A) builds the graph, its schema, the loader and the query shell every later slice imports. S-18 (queries and the REQ-4.3 check), S-19 (visualize) and S-20 (workspace, contracts and `impact`) then touch disjoint files.

**Tech Stack:** As Phases 1 and 2: Node ≥ 22, ES modules, `node:test`, `node:child_process` for git and `gh`, `node:crypto` for hashes, `node:http` for visualize, `node:vm` to run the page's script in tests, no dependencies (D-04). `git fast-import` generates the 10,000-commit fixture.

**Spec:** `docs/spec/04-traceability-graph.md` (REQ-4.1 to REQ-4.8), with the paths of REQ-1.1 and the IDs of REQ-1.9 in `docs/spec/01-layout-and-state.md`, the fixture rule of `docs/spec/05-kit-quality-and-release.md` (REQ-5.2: the graph tested against a fixture repository with real commits, including the 10,000-commit case), and contract C-1 in `docs/spec/contracts/`. Decisions: `docs/decisions.md` (D-04, D-11, D-13, D-15 and D-23 bind this phase).

## Decisions this phase adds

- D-44: `builtAt` is the committer date of the default-branch commit the graph was built from (S-17).
- D-45: a `verdict` node kind, and `in` edges from a pull request and a verdict to their slice (S-17).
- D-46: `testFiles` in config names the test files by path pattern, language-neutral (S-17, S-18).
- D-47: the workspace file is the only list of repositories; `repos` in config is accepted and unread (S-20).
- D-48: a contract's party outside the program is named in words; `check` requires that each side names someone (S-20).
- D-49: bookkeeping pushes skip the team command jobs, and `ci.shards` splits the test job per operating system (S-32).
- D-50: a slice commits the kit's config with `build config`; the kit-file guard skips the default branch's commits and judges a merge by its resolution (S-33).
- D-51: the gate job keeps the pull request cache between runs with `actions/cache` (S-34).

## Global Constraints

Every constraint of `docs/phases/P1-spine/P1.md` and `docs/phases/P2-loop/P2.md` holds, except the commit trailer. In addition:

- **Zero dependencies (D-04).** Node built-ins only, in the kit and in the page visualize writes.
- **Deterministic (D-13).** No wall clock, random number, locale, absolute path, host name or environment value reaches the graph; host answers are the one outside input, and the same answers give the same bytes. Every test that builds twice compares bytes, not parsed objects.
- **No model call, no source parsing (REQ-4.2, REQ-4.8).** The builder reads a non-markdown file only when `testFiles` matches its path, and from it only the lines that hold a REQ ID; `git log` supplies touched paths, never contents. Nothing infers calls, imports or classes.
- **One door to the host (C-1).** Only `slicekit graph` calls the host, only through `getHost`, and only `getPullRequest`. Queries and visualize run no git and no host call. Tests set `SLICEKIT_GITHOST_FIXTURE`, or pass a stub host to `buildGraph` in process for the offline cases; no test reaches the network.
- **Performance (REQ-4.5).** Each query, `status` included, answers in under two seconds of wall time, Node's start included, on the 10,000-commit fixture. The fixture is generated inside the test that times it, in `os.tmpdir()`, with one `git fast-import` (no hooks run, no per-commit process), and is never committed. A full build of that fixture takes under 30 seconds, as an alarm rather than a promise.
- **Subcommand output.** As P2: the first stdout line is the value (`graph` prints the graph file's repository-relative path; a query prints its answer); exit 0 success, 1 refused, 2 usage or unknown ID. `--json` prints exactly one JSON document on stdout on every path.
- **Paths through `kitPaths`.** The graph directory is `kitPaths(root, cfg).graph`, the workspace file `kitPaths(root, cfg).workspace`; no module spells either.
- Commits on the kit's own repo end with ONE final block of two lines, `Slice: P3/S-<nn>` immediately followed by `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **An incremental build after a slice branch is deleted.** The deleted branch's unmerged commits leave the graph, and the result equals a full build byte for byte. Pinned by `graph/build.test.js » an incremental build is byte-identical to a full build, after a new commit and a deleted branch` (S-17).
2. **A host that fails halfway.** Pull requests fetched before the failure are cached once; the rest come from the cache marked stale; a re-run with the host back fetches only those. Pinned by `graph/build.test.js » with the host unreachable pull requests come from the cache marked stale` (S-17).
3. **A label holding `</script>` or a line separator.** The inlined graph cannot end its script block early. Pinned by `visualize.test.js » a label holding a closing script tag stays inside the inlined graph` (S-19).
4. **Paths given with backslashes, `./` or a trailing slash.** `history`, `trace --file` and `impact` match them as the POSIX repository-relative path. Pinned by `graph/queries.test.js » a path written with backslashes or a leading ./ finds the same file` (S-18).
5. **Line numbers in files with CRLF endings.** A covers or implements edge names the same line on Windows as on Linux. Pinned by `graph/build.test.js » a test naming a requirement gets a covers edge with its file and line` (S-17), whose fixture writes one CRLF file.
6. **Three 10,000-commit fixtures.** S-17, S-18 and S-20 each generate one in their own test file, so the three run in parallel; once the phase is merged, a follow-up may merge them into one file.

## Order

**Order:** A; B; C

Groups: A, then B, then C. S-17 (A) owns the shared core every later slice imports: the schema, the builder, the loader, the query shell, the test-file matcher and both fixture generators. S-18, S-19 and S-20 (B) run in parallel because their expected changes share no path: S-18 owns four query modules and commands and the REQ-4.3 check; S-19 owns the visualize directory and its command; S-20 owns the workspace, `impact` and its check rule, and is the only one of the three that changes S-17's builder and graph command. `impact` belongs to S-20, not S-18, because its defining case (REQ-4.6's scenario) is a contract across repositories; each of the three times its own queries on the 10,000-commit fixture. S-30 (B) joins them: it fixes how `build finish` and `status --sync` read CI, judging a commit by the newest run of each workflow (issue #33), and touches only the git host adapter. S-32 (B) makes CI faster: bookkeeping pushes skip the tests and Windows runs in shards (D-49); it touches only the workflow and its generator. S-31 adds a guard test that every test file under `test/` names a requirement, and tags the files that name none. S-33 and S-34 (C) are fix slices for open issues, and they run after group B because each changes files a slice of B built: S-33 changes the git host adapter (S-30) and the build and review steps, and S-34 changes S-18's history, S-19's page, S-20's workspace and S-32's workflow. They run in parallel because their expected changes share no path. S-33 owns the build and review loop: the kit-file guard of `build commit` and a new `build config` step, the review worktree, the brief, how CI runs are read and walked, and the shard script with the two review test files it splits. S-34 owns the graph and the page: the workspace collision rule, the history order, the pull request labels of visualize, the pull request cache and the gate steps that keep it. S-31 moved from B to C with them, so nothing waits on it: it changes only test files. It and S-33 both touch the two review test files, which S-33 splits; the split files carry their requirement comment, so S-31 leaves them alone. S-35 (C) is the 0.2.0 release: the version, the README status and install line, the help on standard output and the changelog. It is built last, after S-33 and S-34 merge, so its changelog and rendered files carry theirs; it sits in C rather than a later group so it does not wait on S-31.
