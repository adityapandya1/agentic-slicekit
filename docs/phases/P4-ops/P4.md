# Phase 4 — Ops: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan slice by slice, task by task. Steps use checkbox (`- [ ]`) syntax for tracking. Each slice file `S-<nn>-*.md` in this folder is one unit of work with its own tasks; this file holds what every slice shares.

**Goal:** A team can close a phase with a release record, find which slices are behind a symptom, and ask which claims of its spec and runbook still hold, without the kit changing anything it was not asked to; CI runs the team's monitoring steps; and the kit itself ships from CI with provenance, with three examples, a user guide and a config that migrates forward.

**Architecture:** Each command is a deterministic `slicekit` subcommand plus a procedure that tells the agent how to use it: the agent reads and judges, the subcommand gathers, checks and writes. No subcommand of this phase calls a model.

- **The runbook judgement** (S-21) is one function, `runbookVerdict`, used in three places: `build pr` before it opens a pull request (it refuses there today on a whole-file test), the new `runbook` check rule on a slice branch, and `slicekit release` for each merged slice. A section is changed when a line of the diff between the merge base and the tip falls inside a `##` section of the runbook (proposed D-55).
- **The release** (S-21) runs on a work branch cut by `slicekit branch release <slug>`. `slicekit release P<n>` refuses unless every slice of the phase is `merged` and passes the runbook judgement; then it writes the release record `P<n>.md` in the docs root's releases directory, sets each slice `released` through `setState`, and rewrites `BUILD.md`. It commits nothing: the procedure opens a `[release] P<n>` pull request with `slicekit pr open`, which commits the record, the state files and `BUILD.md` (proposed D-54). The record is built from files, git and the host only, so two runs on the same inputs give the same bytes.
- **Observability steps** (S-22) come from two places: `ci.observabilitySteps` in config, as today, and a table under `## CI steps the monitoring setup requires` in `observability.md` (proposed D-56). `workflowState(root, cfg)`, which `slicekit workflow` and `init` already call, reads the doc and hands `renderWorkflow` one list.
- **Ops and audit** (S-23) each have a context subcommand that gathers what REQ-2.13 and REQ-2.14 hand the agent (`slicekit ops context`, `slicekit audit context`) and a check subcommand that refuses a report whose rows cite nothing real (`slicekit ops check`, `slicekit audit check`). Reports live in the kit's reports directory, .slicekit/reports, which git ignores, so neither command changes a tracked file (proposed D-57, D-58). The ops agent loses `Write` and `Bash` from its tool list, which is REQ-2.13's enforcement.
- **Config migration** (S-24): `migrateConfig(cfg)` returns the config at `CONFIG_VERSION` and the list of changes. `main()` writes the migrated file and prints the changes before any command but `hook`; a hook migrates in memory only (proposed D-60).
- **Publishing** (S-24) is a second, hand-written workflow run on a pushed version tag. How it authenticates to npm, and which repository and npm settings it needs, are the author's to answer (Open D-62); its actions are pinned by SHA from the same pins file as the generated workflow.

**Tech Stack:** As Phases 1 to 3: Node ≥ 22, ES modules, `node:test`, `node:child_process` for git and `gh`, no dependencies (D-04). The publish workflow uses `actions/checkout` and `actions/setup-node` at the SHAs in `templates/workflow/pins.json`.

**Spec:** `docs/spec/02-commands-agents-loop.md` (REQ-2.9, REQ-2.13, REQ-2.14), `docs/spec/03-hooks-gates-ci.md` (the runbook row of REQ-3.7, REQ-3.11), `docs/spec/04-traceability-graph.md` (REQ-4.8), `docs/spec/05-kit-quality-and-release.md` (REQ-5.5 to REQ-5.8). Decisions: `docs/decisions.md` (D-12, D-13, D-19, D-20, D-21, D-28, D-33, D-41, D-43, D-47 and D-53 bind this phase).

## What already exists

- `released` is a state, reached only from `merged` with `--release <file>` naming the slice's pull request (`src/state/transitions.js`); `BUILD.md` counts `merged` and `released` alike as Done.
- `/slicekit release`, `/slicekit ops` and `/slicekit audit` are rendered into `.claude/commands/` and each runs `slicekit instructions --command <name>`, which exits 1 with `the /slicekit <name> command is not built in this version`: the three procedure templates under `templates/instructions/commands/` are missing. The ops and auditor briefs under `templates/instructions/agents/` exist.
- `ci.observabilitySteps` is validated in `src/config.js`, and each step renders as an `obs-<n>` job that `SLICEKIT_CHECKS_OK` requires (`src/workflow.js`). Only the doc half of REQ-3.11's sentence is missing.
- `build pr` refuses a runbook-flagged slice whose branch did not change the runbook file and whose notes give no `no operational change` line. No check rule judges the slice after that.
- The graph reads release records (`release` nodes, `released-in` edges, `shipped`), and `history` answers per path; ops and audit read both.
- The README walkthrough runs verbatim as `test/walkthrough.test.js` inside the test job, which runs on Linux, macOS and Windows; `docs/adapters.md` describes C-1 to C-3. S-24 keeps both.
- `CONFIG_VERSION` is 1 and `validateConfig` refuses any other value; nothing migrates.

## Global Constraints

Every constraint of `docs/phases/P1-spine/P1.md` and `docs/phases/P2-loop/P2.md` holds, except the commit trailer; the constraints of `docs/phases/P3-trace/P3.md` hold for anything that reads the graph. In addition:

- **Commands own git (D-19).** No procedure under `templates/instructions/commands/` holds a `git` or `gh` command; the brief lint covers the three new ones. `slicekit release`, `ops context` and `audit context` only read git; `pr open`, already built, commits and pushes.
- **Reports change nothing tracked.** `ops` and `audit` write only in .slicekit/reports. Each test of either ends by asserting that `git status --porcelain` is empty.
- **Deterministic records.** The release record holds no wall-clock time, user name, machine name or absolute path; its date is the committer date of the default-branch commit it names. A test writes it from two clones and compares bytes.
- **One door to the host (C-1).** `release` reads pull requests only through `getHost` and `getPullRequest`. Tests set `SLICEKIT_GITHOST_FIXTURE`; no test reaches the network, and no test publishes.
- **Publishing is the author's.** No slice publishes, changes a repository setting, creates a secret or pushes a tag. S-24 writes the workflow and the runbook steps; the author does the rest by hand once D-62 is answered.
- **Subcommand output.** As P2: the first stdout line is the value (a path, `#<n> <url>`); findings one per line as `<file>:<line> <message>`; exit 0 success, 1 refused or findings, 2 usage or unknown ID.
- **Rendered files.** A template change under `templates/claude-code/` reaches the kit's own `.claude/` through `build render` (D-43), never by hand.
- Commits on the kit's own repo end with ONE final block of two lines, `Slice: P4/S-<nn>` immediately followed by `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **A runbook change that is not a section.** A diff that touches only the `#` title line, or only trailing whitespace, changes no section; deleting a whole section does. Pinned by `check/runbook.test.js » a change above the first section heading is not a section change` (S-21).
2. **A release run twice.** The second run refuses because the record exists, and the first run's bytes do not depend on the clock or the clone. Pinned by `commands/release.test.js » the record is byte-identical from two clones at the same commit` (S-21).
3. **A doc step and a config step with one name.** Refused, naming both places, so a job never drops out of `SLICEKIT_CHECKS_OK` unseen. Pinned by `observability.test.js » a step named in observability.md and in config is refused, naming both` (S-22).
4. **A symptom word that matches half the repository.** `release` in the kit's own tree matches dozens of files; ops reports it as too broad instead of handing the agent every file. Pinned by `commands/ops.test.js » a word that matches more than fifty files is reported as too broad` (S-23).
5. **A config migration in a hook.** A hook reads an older config and never writes it; the next plain command writes it once. Pinned by `config.test.js » a hook reads an older config without writing it` (S-24).

## Order

**Order:** A; B; C

Groups: A, then B, then C, as the stubs had them. S-21 and S-22 (A) run in parallel because their expected changes share only the shared roots (`docs/runbook.md`, test files and `src/cli/index.js`): S-21 owns the runbook judgement, its check rule, `build pr`'s use of it, the release command, the `[release]` title and the release procedure; S-22 owns the observability doc parser, the workflow generator, the intake procedure's table shape and the backend example's observability file. S-23 (B) comes after S-21 because ops hands the agent the last release record, and its fixtures carry one written by `slicekit release`. S-24 (C) comes last because its user guide has a page for every command and rule, the release, ops and audit ones included, and its examples are rendered after S-21 to S-23 changed the templates. S-24 is the largest slice of the phase. Its publish task waits on the author's answer to D-62; if D-62 is still open when the rest of S-24 is done, the publish task moves to a slice of its own in group C rather than holding the slice back.
