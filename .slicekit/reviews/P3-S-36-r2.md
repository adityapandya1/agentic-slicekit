## Candidate fix (working tree, not the reviewed head)

The uncommitted change to `src/git.js` and `test/default-branch.test.js` drops the HEAD-branch step: origin's HEAD (only while its branch exists, or in an empty repository); else the first of init.defaultBranch, main and master that is a local branch or that an empty repository's HEAD is on; else main.

- It resolves B-1: `node --test test/default-branch.test.js test/init.test.js test/githooks.test.js test/check/trailer.test.js` → "# pass 88", "# fail 0"; `node --test test/githooks-time.test.js` → "# pass 1", "# fail 0". A slice branch, unborn or with commits and no main → `main ["main"]`, commit allowed.
- Issue #78: plain `git init -b master`, empty → master; with one commit → master, `graph` exit 0.
- A global init.defaultBranch (GIT_CONFIG_GLOBAL set to trunk): master repo, empty or with a commit → master; an empty repository on trunk → trunk; an empty repository on feature → main.
- An empty clone whose origin HEAD names develop → develop. Origin HEAD naming main with HEAD on an unborn slice branch → main, commit allowed.
- It does not resolve B-2 or H-5, which are in the pull request body.
- It makes Done when 1 ("else the branch HEAD is on"), `CHANGELOG.md` lines 9 to 11 ("else the current branch, an empty repository's too") and the evaluation-set note on `init.test.js` describe an order the code no longer has; those need changing in the same round.
- The issue #87 case (trunk repo, no origin, feature branch checked out) now writes main, a branch that does not exist: trunk is unprotected and `graph` stops with "the default branch main is not present here". That is 0.2.0's behaviour, not a new hole, and it no longer protects the feature branch. An empty repository on develop with no init.defaultBranch also writes main, as 0.2.0 did.
